# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Crop Guardian is a Bengali, mobile-first Next.js app that advises potato farmers in Bangladesh on late blight. It has a weather-based daily risk, on-device leaf photo diagnosis that admits when it is unsure, and SMS sign-in for farmers and agriculture officers. README.md is the detailed spec for each feature's behaviour. Read it before changing a feature, and keep it up to date when behaviour changes.

## Next.js 16 caveat

This project uses Next.js 16 / React 19, which have breaking changes compared with older Next.js versions. Before writing Next-specific code, read the relevant guide in `node_modules/next/dist/docs/` and follow its deprecation notices. For example, request interception lives in `src/proxy.ts` (exporting `proxy`), not `middleware.ts`. `AGENTS.md` is regenerated by `next dev`, so leave it as is.

## Architecture

**Three independent subsystems, plus SMS alerts on top of the first and third, and an assistant and MCP server on top of the first.** Most of the app works signed out and offline. Only `/account` and `/officer` need an account.

1. **Weather risk (server, no ML).** `src/lib/weather.ts` fetches Open-Meteo hourly forecast or archive data at the farmer's union (Shibganj, Bogura, by default and for the backtests). The areas (17 potato districts of the Rangpur and Rajshahi divisions and Munshiganj, down to unions) are in `src/lib/areas.ts`, built by `scripts/build-areas.ts`; it is server-only, and the phone reads the place from the `cg-union`/`cg-place` cookies (`placeCookies.ts`). Two crops share it: `src/lib/risk.ts` applies the Hutton criteria (potato late blight), and `src/lib/blast.ts` applies a draft rice-blast rule (paddy, labelled experimental). `risk.ts` also holds the shared parts (`classifyRun`, `overallRisk`, `buildDecision`). **`src/lib/crops.ts` is the registry of crops and seasons (potato, boro, aman): names, titles, decision text, rule and season windows. Screens read it instead of naming আলু, ধসা or Hutton.** `src/app/page.tsx` (Home) renders every crop's panels from one forecast. `GET /api/risk?crop=` and `/api/risk/season?crop=` use the crop's rule. `src/lib/season.ts` limits risk to a field's in-field window. Fields (at most one per season, with the season as the id) are kept in localStorage by `fields.ts`, which also migrates the old single potato date. Their parsing and season checks are in `fieldList.ts`, which has no React or storage, so server code can use it. Because the server can't read localStorage, Home renders as if no field is set, and `FieldsGate` corrects it on the client (one chip per field in season). The ledger shows no savings for paddy (`calendarBaseline: false`).

2. **Diagnosis (entirely client-side).** It is in `src/lib/diagnosis/`, and the flow runs camera → result screens:
   - `CameraScreen` checks photo quality without ML (`imageQuality.ts`) and saves two JPEGs to IndexedDB (`captureStore.ts`, which also stores results, answers and shared cases).
   - `worker.ts` runs onnxruntime-web (wasm, single thread) in a Web Worker. `client.ts` and `useDiagnosis.ts` are the main-thread side. The model and wasm are kept in the Cache API.
   - `preprocess.ts` → `decide.ts` (temperature softmax, conformal set, OOD) → `combine.ts` (each photo is decided on its own, then the more cautious result wins: unknown > uncertain > confident).
   - `flow.ts` maps a decision to its route (`/result`, `/result/uncertain`, `/unknown`), and `questions.ts` narrows uncertain candidates using the farmer's answers.
   - **Each crop's classes, Bengali labels, preprocessing constants, temperature and thresholds come from its exported config, parsed by `config.ts`** (potato: `public/model/crop_guardian_config.json`, from an external notebook; paddy: `public/model/paddy/`, from `notebooks/paddy_training.ipynb`). Never hardcode them. `src/lib/diagnosis/crops.ts` is the per-crop registry: config URL, the class ids and Bengali labels the advice and questions were written for (tested against the config), the two photos' instructions, and `PHOTO_CROPS`, the crops whose model is in place (potato and paddy; paddy is labelled experimental). The worker loads one crop's model at a time; a `DiagnosisRecord` carries its `crop` (none means potato, via `cropOfRecord`). `content.ts` and `questions.ts` are keyed by crop; question ids are unique across crops. `__fixtures__/parity/` (potato) and `__fixtures__/parity-paddy/` hold the notebooks' reference outputs.
   - `scripts/copy-ort.mjs` (run on postinstall, predev and prebuild) copies the ORT wasm into the gitignored `public/ort/<version>/` and writes `sizes.json` for the download progress bar. Nothing is loaded from a CDN.
   - `?mock=confident|healthy|uncertain|unknown` (`mock.ts`) drives the screens without the model. Demo answers ride in the URL (`a=rings.no`) so demos never touch device data.
   - `shareCase.ts` sends a case to an officer through the Web Share API, falling back to a WhatsApp link. No server is involved.

3. **Auth.** Better Auth (`src/lib/auth/auth.ts`, served by `src/app/api/auth/[...all]`) uses the phone-number OTP plugin and stores users, sessions, codes and rate limits in Neon Postgres. `auth.ts` must not import `server-only`, because the Better Auth CLI loads it outside Next. `src/proxy.ts` only does an optimistic cookie check. The real checks are `requireUser` and `requireOfficer` in `src/lib/auth/session.ts`. Phone numbers are normalized to E.164 `+8801XXXXXXXXX` in `src/lib/phone.ts`, which also accepts Bengali digits. `src/lib/sms.ts` sends through the SMS Gate API, and in development it prints the SMS to the console when `SMS_GATE_*` is unset. The `role` field (`farmer` | `officer`) has `input: false`. Env vars: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMS_GATE_USERNAME`, `SMS_GATE_PASSWORD`, `CRON_SECRET` (via `vercel env pull .env.local`).

4. **SMS alerts.** A signed-in farmer opts in on `/account` (`AlertToggle` → `setAlerts`), which copies their union and fields to the `"alert"` table (`src/lib/alertDb.ts`; `/planting` keeps the copy in step). Vercel Cron (`vercel.json`, 16:00 BST) calls `/api/cron/alerts` with `CRON_SECRET`, and `alertRun.ts` texts each farmer through `sendSms` when today or tomorrow is danger for a crop in their field. The pure rules are in `alerts.ts`: `nextAlert` sends one SMS per run of danger days (the same quiet-days rule as `backtest.ts`, state in `"alert_state"`), and `alertMessage` must stay ≤ 70 characters (one UCS-2 SMS, tested). Home's decision promises "SMS-এ জানাব" only to a viewer with alerts on (`viewerHasAlerts`); everyone else is told "আবার দেখে নিন". Tables come from `npm run db:migrate` (`scripts/migrate-cases.ts`).

5. **Assistant and MCP (server, LLMs through the Vercel AI Gateway).** `src/lib/assistant/`: `kb.ts` builds the knowledge base only from text the app already shows (potatoGuide, guide, diagnosis content, crop decisions), so the assistant can never say more than the screens. `answer.ts` runs rewrite (Haiku, structured output) → `retrieve.ts` (pgvector + Postgres full-text over stems from `tokens.ts`, fused by `rrf`, Cohere rerank, each step degrading rather than failing) → answer (Sonnet with `searchGuide`/`todayRisk` tools and structured output) → `guard.ts` (dose filter, invented-source filter, phone redaction). `answer.ts` must not import `server-only` (the eval script runs it); `server.ts` wires the DB, place cookie and daily limit. Model ids live only in `models.ts`, prompts only in `prompts.ts`: **bump `PROMPT_VERSION` when a prompt changes** and re-run the eval. The instructions are cached, so keep anything per-question (date, place, sources) out of them (tested). `/api/mcp` (`mcp-handler`) exposes the same engines as read-only tools; its pure parts are in `src/lib/mcpTools.ts`, and `src/lib/riskAt.ts` is shared with the assistant. Env: `AI_GATEWAY_API_KEY` or `VERCEL_OIDC_TOKEN` (from `vercel env pull`, expires after ~12 h), `MCP_SECRET` (optional; set it in production).

**Offline.** `public/sw.js` is a hand-written service worker, registered only in production builds by `ServiceWorker.tsx`. It precaches the diagnosis pages plus the hashed `/_next/static` assets it scrapes from their HTML. Pages are network-first. Home, `/ask` and the signed-in pages (`/account`, `/officer`, `/sign-in`) are deliberately not cached, so a stale risk or a signed-in page is never shown offline. They fall back to `/offline`. If you add a page to the offline diagnosis flow, add it to `PAGES` in `sw.js`, and bump `SHELL` when the cache contents change. `next.config.ts` serves `sw.js` with no-cache headers.

**Static data.** The map, the ledger and Home's sample fallback still use `src/lib/data.ts`. `/potato` (`potatoGuide.ts`) is Bangladesh-only growing advice with sources; keep Indian places and doses out of it (tested).

## Conventions

- All user-facing text is Bengali, except `/docs`, which is in English for judges and partners and is built from the reports in `docs/` (`src/lib/docsData.ts`). Use `src/lib/bn.ts` for digits (`toBnDigits`, and `fromBnDigits` for input), weekdays and dates. Dates are handled as `YYYY-MM-DD` strings in a time-zone-independent way (`src/lib/dates.ts`).
- Generated risk text must fit in two lines on a phone, and the tests guard its length. Danger days are named from the forecast, never as fixed weekdays.
- Diagnosis advice in `content.ts` never gives a dose (it always says "লেবেল অনুযায়ী"). Results answered through questions are labelled differently from model-confident ones, and every result carries the "পরীক্ষামূলক" (experimental) note.
- The UI is phone-sized (`PhoneFrame`, max 390px) and styled with Tailwind v4 (`src/app/globals.css`). The camera and the service worker need a secure context, so use `localhost` or `next dev --experimental-https` on a phone.
- Code style: no semicolons, single quotes, and short comments that explain *why*.
